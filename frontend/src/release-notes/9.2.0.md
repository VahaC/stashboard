## Highlights

**Update now** finally works on the one container you most want to keep current: **Stashboard
itself**.

Until now, clicking **Update now** on Stashboard's own watch broke the instance. A container
can't recreate *itself* from the inside — the moment Stashboard stopped and removed its own
container, the process doing the work died, so the new container never got created and your
instance simply vanished.

**9.2** detects this case and does the right thing instead: it hands the update off to a
short-lived **helper container** that recreates Stashboard from the outside and then cleans
itself up. You click **Update now**, see a *"Self-update scheduled"* message, the UI blinks
out for a few seconds while it restarts — and comes back on the new version.

## The details

### Self-update, the safe way

When the container you're updating is Stashboard's own, Stashboard no longer tries to recreate
itself in place. It launches a **detached one-shot helper** — the very same Stashboard image,
run in a special self-update mode — that inherits Stashboard's mounts and connection details
and performs the normal pull + recreate from outside. Because the helper is its own container,
it survives Stashboard restarting and finishes the job, then removes itself automatically so it
never lingers.

This covers **both** buttons: **Update now** on the Stashboard container, and **Update project**
when the Compose project includes Stashboard — the whole project recreate is handed off the same
way.

Stashboard recognises "itself" by matching the running container's **id**, so this works no
matter how the connection reaches Docker — a **local socket, an SSH tunnel, or TCP** — and a
container running on a genuinely *remote* host is correctly never treated as self.

It works exactly like a regular update otherwise: a **Compose-deployed** Stashboard is
recreated with `docker compose up -d`, and a plain `docker run` deployment uses the raw
recreate. Nothing to configure.

### A new "Scheduled" outcome

Because the recreate now happens out of band, a self-update is first recorded in the watch's
**Update history** as **Scheduled** — the work is handed off, not finished on the spot. The
scheduled entry remembers the exact image the update is aiming for. When Stashboard comes back
up, it **confirms the result**: it reads the container's actual running image and compares it to
that target. Match → the entry becomes **Success** and the *"Update available"* badge clears.
Mismatch (the update didn't take) → it becomes **Failed** and the badge stays, so you know to
look. No optimistic guessing, and it works even if your registry is unreachable at that moment.
The confirmation dialog shows the matching *"Self-update scheduled"* banner and warns you the UI
will be briefly unavailable.

### Under the hood

The bundled Docker Compose binary baked into the image was bumped from **5.1.4 to 5.2.0**.

## Requirements

This rides on the existing **Update now** feature, so the prerequisites are the same — there's
no separate switch to flip:

- The connection must be able to **recreate** the container — the same as any "Update now". For
  a local socket that means mounting it **writable**
  (`- /var/run/docker.sock:/var/run/docker.sock` — **without** the trailing `:ro`); an **SSH**
  or **TCP** connection works too. A read-only socket is enough for update *monitoring*, but
  recreating a container — including Stashboard itself — needs write access.
- Add a **watch** for the Stashboard container (its image + container name), the same as any
  other tracked container. The **Update now** button then appears on that watch.

See **DOCKER_UPDATE_MONITORING_GUIDE.md → §5.1 "Updating Stashboard itself"** for the full
walkthrough.

### Heads up

- Updating a container on a genuinely *remote* host is unaffected — it's correctly never
  treated as self and behaves exactly as before.
- Expect a few seconds of downtime while the container restarts; refresh the page after about
  a minute if it doesn't reload on its own.
