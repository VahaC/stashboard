## Highlights

If you already run an identity provider — **Authentik**, **Authelia**, **Keycloak**, or anything that
speaks **OpenID Connect** — your homelab probably wants Stashboard *behind it*, not maintaining a
separate password. **10.5** adds **OIDC single sign-on**: configure a provider once and a
**“Sign in with …”** button appears on the login page.

It's **additive and optional**. Local password login (and **two-factor**) keep working exactly as
before — SSO sits alongside them. Off by default; nothing changes until you turn it on.

## The details

### Configure a provider in one place

Under **Settings → Single sign-on**, point Stashboard at your provider:

- a **button label** (e.g. *Authentik*), shown as *“Sign in with Authentik”*,
- the **issuer URL** — Stashboard reads `{issuer}/.well-known/openid-configuration` for the
  endpoints and signing keys, so there's nothing else to type by hand,
- the **client ID**, and an optional **client secret**,
- the **scopes** (default `openid profile email`), and
- the **redirect base URL** — the page shows the exact **redirect URI** to register at your provider,
  with a copy button.

A **“Test discovery”** button confirms the well-known document loads before you ever attempt a real
sign-in. The client secret is **encrypted at rest** and, like every other secret in Stashboard,
**never returned** to the browser — the form only shows whether one is stored. Leave the secret blank
to run as a **public (PKCE-only) client**, which Authelia and others prefer.

### Secure by construction

Stashboard uses the **Authorization Code flow with PKCE**, validates the provider's identity token
against its published signing keys, and checks a one-time `nonce` — so an intercepted or replayed
redirect can't sign anyone in. The SSO session is the **same** access + refresh token pair the rest
of the app already uses, so everything downstream behaves identically to a password login.

### Account linking by verified email

An OIDC identity is matched to a Stashboard account by its **verified email** (your provider must mark
the address as verified — Stashboard refuses an unverified one). The first SSO sign-in **links** the
account and remembers the provider's stable user id, so a later email change in the provider doesn't
break sign-in.

- With **Allow OIDC registration** on, a first sign-in for an **unknown** verified email **creates** a
  new account automatically.
- With it off (the default), the user must **already exist** — SSO just becomes a second way in.

A provisioned account has **no password** until you set one (via *Forgot password*), so it can only
ever sign in through SSO until then.

### Optional: SSO-only accounts

A linked account keeps its password by default. If you'd rather lock an account to SSO, open
**Account → Single sign-on** and **disable local password sign-in**. There's a safety net: if the
OIDC provider is ever turned **off** at the server, password login is **automatically re-allowed** so
you can never lock yourself out.

### In your backups

The OIDC provider configuration (with the secret **re-encrypted** for the destination instance) and
each account's link + local-login flag are included in **Backup / Restore** and survive a round-trip.

## Using it

1. Go to **Settings → Single sign-on**.
2. Fill in the **button label**, **issuer URL**, **client ID** and (optionally) the **client secret**.
3. Copy the shown **redirect URI** and register it in your provider's app/client config.
4. Click **Test discovery** to confirm the issuer is reachable, then tick **Enable single sign-on**
   and **Save**.
5. (Optional) tick **Allow OIDC registration** if a first SSO login should create accounts.
6. Sign out — the login page now shows **“Sign in with …”**.

To link your own account, just sign in once through the button. To make your account SSO-only,
disable local login under **Account → Single sign-on**.

## Not included yet

This release covers OIDC login. **SAML**, **SCIM** user provisioning, **group/role mapping**, and
enforcing **OIDC-only** for the whole instance are not part of 10.5.
