## Highlights

This release adds the **disaster-recovery** leg of Proxmox container provisioning:
re-create an LXC from an existing `vzdump` backup archive, right from Stashboard.
Together with **create from template** (6.13.1) and **clone** (8.0.0), every "make a
container" path in the Proxmox UI is now mirrored here.

## Turning it on (off by default)

Restore is **off until you enable it**, and it takes **two** switches — a server-wide
master switch and a per-host opt-in. Until both are on, the **Restore LXC** button
won't appear (and the server refuses a restore request regardless):

1. **Enable it server-wide.** Go to **Settings → Restore LXC** and tick
   **Enable restore LXC server-wide**, then **Save**.
2. **Opt the host in.** On the **Proxmox** page open the host's menu (**⋮ → Edit**),
   tick **Allow restore**, and save.

Once both are on, the **Restore LXC** button shows up in the host's header menu
(**⋮**), next to **New LXC**. (PVE hosts only — Proxmox Backup Server hosts aren't
supported here. The archive dropdown is empty until the node has at least one
file-based `vzdump-lxc-*` backup.)

## Restore LXC from a backup

The **Restore LXC** button opens a dialog where you choose:

- a **backup archive** — the dropdown lists the `vzdump-lxc-*` archives across the
  node's backup-capable storages, each shown with its guest id, timestamp and size,
- a target **VMID** (pre-filled from the cluster's next free id, with one click to
  **Use original** — the id the archive was taken from),
- an optional root-filesystem **storage** (blank keeps the storage each volume was
  backed up from), and
- the **unprivileged** / **start after restore** toggles.

The restore runs as a real Proxmox task that Stashboard polls to completion, so you
get a genuine success/failure result. On success the host is re-scanned and the
restored container shows up immediately.

### Overwriting an existing container

Restoring **over** an existing VMID replaces that container — so it is gated: the
target must be **stopped**, and you have to clear an explicit **double-confirm** that
names the exact container being replaced. Restoring to a new (unused) VMID needs no
confirmation.

### Safety & audit

The two switches above are gates, not just a hidden button — with either one off the
server refuses the request. Every attempt that reaches the host is recorded on the
Audit page's new **LXC restore** tab (who, when, host, node, vmid, backup, whether it
overwrote an existing container, and the result). A host rejection is surfaced
verbatim.

### Not included yet

Restoring from a **Proxmox Backup Server** datastore, bandwidth limiting, and
live-restore are deferred to a later release.
