## Highlights

Until now, every call to the Stashboard API needed a **short-lived login token** — the same one your
browser gets when you sign in. Great for the app, painful for everything else: to point a script,
a cron job, or an external monitor at Stashboard you had to **store your password** and replay the
whole login/refresh dance.

**10.4** fixes that with **personal access tokens (PATs)** — long-lived, named, **scoped**,
**revocable** keys you create once and paste into a script. Send one as
`Authorization: Bearer sb_pat_…` and the API treats the request as you. It's the standard
self-hosted expectation, and it's here.

## The details

### Create a token in seconds

Under **Account → API tokens**, click **Create token**. You choose:

- a **name** (e.g. *"Grafana scraper"* or *"backup cron"*) so you remember what it's for,
- a **scope** — **Read-only** (only `GET` requests) or **Full** (read and modify your data),
- an **expiry** — **30 / 60 / 90 days**, **Never**, or a **custom date**.

Because minting a long-lived key is a security-sensitive step, creating one asks for your
**current password**.

### Shown once, stored hashed

The moment you create it, Stashboard shows the **full secret** (`sb_pat_…`) **exactly once** with a
**Copy** button. Save it then — once you close that panel it's gone for good. We never store the
secret itself, only a salted **hash** of it (the same way passwords and refresh tokens are kept), so
even a database leak can't reveal your tokens. The list afterward shows only a short **hint**
(`sb_pat_AB12…`), the scope, the expiry, and **when the token was last used**.

### Use it from anything

Send the token as a bearer header on the same endpoints the app uses:

```
curl -H "Authorization: Bearer sb_pat_…" https://your-stashboard/api/services
```

Stashboard resolves it to **your** account. A **Read-only** token is accepted on `GET` requests and
**refused (403) on anything that changes data** — so a key you drop into a dashboard or a status
probe can't accidentally (or maliciously) modify your setup. A **Full** token can do both.

### Revoke instantly; survives password changes

Hit **Revoke** on any token and it stops working on its **very next request** — same for one that
hits its expiry date. Each token also records a **last-used** time so you can spot stale or
suspicious keys and clean them up (**Delete** removes a revoked token from the list entirely).

Unlike your browser sessions, PATs are **independent of your password**: changing your password or
using **"sign out everywhere"** does **not** kill your tokens, so your automation keeps running
through a routine credential rotation. To stop a token you **revoke it** (or delete your account,
which removes them all).

### Kept away from the dangerous surfaces

A PAT is for the **REST data surface only**. By design it can **never**:

- open the **host terminal** or **exec into a container** (those keep their own one-time,
  interactive-session ticket flow), or
- touch **account security** — changing your password or email, managing two-factor auth, deleting
  your account, editing the SMTP or Telegram settings, or managing tokens themselves.

Try any of those with a token — even a Full one — and you get a clean **403**.

### Not in your backups

Personal access tokens are **bearer secrets**, so — like refresh tokens — they're **not** included
in **Backup / Restore** (exporting them would either leak them or be useless). After restoring onto a
new instance, just mint fresh tokens.

## Using it

API tokens are available to **every account** — there's nothing to switch on at the server level.

1. Go to **Account → API tokens** and click **Create token**.
2. Give it a **name**, pick a **scope** (Read-only or Full) and an **expiry**, and confirm with your
   **password**.
3. **Copy the secret** shown on the next screen — it won't be shown again.
4. Send it on API requests as `Authorization: Bearer sb_pat_…`.

Revoke or delete a token any time from the same page.

## Not included yet

This release covers scoped bearer tokens for the REST API. **OAuth / third-party app authorization**,
**finer per-endpoint permissions** beyond Read-only vs Full, and **token usage analytics** beyond the
last-used timestamp are possible later — not part of 10.4.
