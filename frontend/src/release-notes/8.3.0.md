## Highlights

The **restore-from-backup** workflow that shipped for LXC containers in 8.1.0 now
works for **QEMU/KVM virtual machines** too. Lost a VM, or want to roll a whole
machine back to last night's `vzdump`? Re-create it from an existing backup archive —
to a new id, or (carefully) over an existing one — straight from the Stashboard
Proxmox page, without opening the Proxmox web UI. It's the exact same surface as the
container restore, not a parallel one.

With this, **every** "make a guest" path in Stashboard — create, clone, restore — is
mirrored for VMs as well as containers.

## Turning it on (off by default)

This reuses the **same** restore gates as 8.1.0 — there is nothing new to enable if
you already turned restore on for containers. It takes **two** switches, and until
both are on the **Restore VM** button stays hidden (and the server refuses the request
regardless):

1. **Enable it server-wide.** Go to **Settings → Restore guest** and tick
   **Enable guest restore server-wide**, then **Save**.
2. **Opt the host in.** On the **Proxmox** page open the host's menu (**⋮ → Edit**),
   tick **Allow restore**, and save.

Once both are on, open the host's actions menu (the **⋮** button in its header) and
pick **Restore VM** (next to **Restore LXC**).

## Restore a VM

The **Restore VM** dialog is the container restore with VM wording:

- **Archive** — a dropdown of the node's `vzdump-qemu-*` backups, each shown with its
  guest id, timestamp and size (or paste a volid by hand). Only VM backups appear
  here — container backups live under **Restore LXC**.
- **VMID** — defaulted to the cluster's next free id; one click on **Use original**
  restores to the id the backup was taken from.
- **Target storage** — where the restored disks land (blank keeps each disk on the
  storage it was backed up from).
- **Name** — optional; blank keeps the backup's name.
- **Start at boot** / **Start after restore** toggles.

Restore calls `POST …/qemu` with `archive=<backup volid>` and polls the task to real
success or failure — not a fire-and-forget "request accepted".

## Overwriting an existing VM

Ticking **Overwrite existing VM** restores **over** a VMID that already exists —
replacing that machine and its disks. Because that's destructive, it requires the
target VM to be **stopped** and an explicit **double-confirm** naming it, exactly like
the container path. Restoring to a brand-new id needs no confirmation.

## Safety & audit

Every restore that reaches the host is recorded on the Audit page's **Guest restore**
tab (who, when, host, node, vmid, backup, whether it overwrote, result) — the same
trail as containers, now covering both kinds. A host rejection (a corrupt archive, a
storage that can't hold the disks) is surfaced verbatim, and a successful restore
re-scans the host so the VM card appears right away.

### Not included yet

Restoring from a **Proxmox Backup Server** datastore, bandwidth limiting, and
live-restore are deferred — same exclusions as the 8.1.0 container release.
